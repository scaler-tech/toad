## C1 — CTA button: no misleading success, no silent drop

**Files:** `internal/slack/interactive.go` (handleInteractive), `internal/slack/responder.go` (new `TicketInProgressBlocks`)
**Commit:** `8bfcec9`

**What changed:**
- The button's pre-fetch flip no longer jumps straight to the final
  ":ticket: Ticket requested by `<user>`" wording. It now shows a
  truthful-in-progress state (`TicketInProgressBlocks`: ":hourglass: Ticket

## C4 — digest: failed chunks must not lose messages

**Files:** `internal/digest/digest.go` (`flush`, new
`requeueOrDropFailedChunk`, `Message.attempts`, `chunk.raw`),
`internal/digest/chunking.go` (`buildChunks` now tracks pre-dedup
`rawByChannel`)
**Commit:** `8b7ba9f`

**What changed:**
- `flush()` now captures `analyzeWithRetry`'s error (previously discarded via
  `opportunities, _ := ...`) and calls `requeueOrDropFailedChunk` instead of
  silently continuing.
- Each message carries an unexported `attempts int` counter. On a chunk
  failure, its **raw** (pre-dedup) messages are re-appended to `e.buffer`
  (under `e.mu`) if `attempts < maxChunkRequeueAttempts` (3); otherwise
  dropped and logged at Error with count. A genuine requeue logs at Warn.
- Requeuing uses `chunk.raw` (pre-dedup originals), not `chunk.messages` (the
  dedup-annotated "(xN duplicates)" copies used for analysis) — this is what
  keeps a later dedup pass working correctly against genuinely new
  duplicates, per `buildChunks`' new `rawByChannel` tracking.
- `flush()` only counts a message toward `e.totalProcessed` when
  `attempts == 0`, so retried messages aren't double-counted in that metric.

**Test evidence:**
- `internal/digest/flush_requeue_test.go` (new file):
  `TestFlush_AnalysisFailure_RequeuesMessagesForNextFlush`,
  `TestFlush_AnalysisFailsMaxTimes_DropsWithoutRequeue`,
  `TestFlush_SuccessPath_Unchanged`.
- `go test ./internal/digest/...` — PASS. `go test -race ./internal/digest/...` — PASS (verified before scope split).

  `ClaudeLastSuccessAt`, `ClaudeLastError`, populated every 10s by the
  stats-writer goroutine from `failureTracker.Snapshot()`.
- `/api/data` surfaces these on `apiDaemon`; the dashboard shows an
  attention-strip alert when `claude_consecutive_failures >= 5`: "Claude
  calls failing (N in a row since `<time>`): `<lastErr>`".

**Test evidence:**

## I1 — explicit ticket path must not file infeasible findings

**Files:** `cmd/ticketflow.go` (`runTicketRequest`, new
`composeInfeasibleTicketReply`, `trimForReply`)
**Commit:** `cb9f3fa`

**What changed:**
- After a **fresh** investigation (not a reused record —
  `reuseRecentInvestigation` already filters infeasible saved records before
  this point), `runTicketRequest` now checks `f.Feasible` before proceeding
  to `FileOrUpdate`. On `!f.Feasible`: the investigation record is still
  saved (mirrors `runTriggeredInvestigation`'s "save before checking
  Feasible" pattern for audit visibility), and the function returns a reply
  (not an error) of the form:
  `":warning: I investigated but couldn't confirm a concrete fix: <reasoning
  trimmed to 300 chars>. No ticket filed — reply with more detail and ask
  again."`
- **Deviation from spec:** the "file it anyway" override phrase is
  deliberately **not implemented** — the spec explicitly called this
  optional ("if non-trivial, skip the override"). Implementing it would
  require plumbing an override signal through `runTicketRequest`'s call
  sites and re-deriving trust for a previously-rejected finding, which adds
  meaningful surface area for a corner case; the reply instead asks the user
  to add detail and re-request.

**Test evidence:**
- `cmd/ticketflow_test.go`: `TestRunTicketRequest_FreshInfeasibleFindingDoesNotFile`
  — asserts zero `CreateIssue` calls, reply contains "No ticket filed" and
  the investigation's reasoning, no error outcome, and the claim is released.
- `go test ./cmd/...` — PASS.
